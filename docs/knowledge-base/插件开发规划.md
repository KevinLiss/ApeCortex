# ApeAdmin 知识库插件开发规划

> 版本 v1.0 · 2026-11-24
> 依据：两轮开源调研（24 仓库代码精读，见 `research/notes/代码精读调研笔记.md`）+ ApeAdmin 框架接入点精读（backend `plugins/ai/mcp/db/core` + frontend `router/views/locales`）
> 目标：开发 ApeAdmin（FastAPI 版）的一级插件 `knowledge_base`，覆盖三大需求：①聊天自动沉淀用户知识/习惯 ②聊天式创建知识库 + AI 自主联网调研成文 ③联网采集与专业论文检索

---

## 一、需求映射与总体架构

```
用户 ──聊天──► ApeAdmin AI 对话
               │ ① _finish_run 事件钩子（宿主+1行）
               ▼
        [记忆层 P0] 判断→提取→画像沉淀（mem0 ADD-only + EverOS 缓冲/双粒度 + graphiti 时序失效）
               │ 画像/事实可被 kb.query 召回注入上下文
               ▼
        [LLM Wiki 编译层 P1] 原始资料→词条编译→审批→发布
               （WeKnora 数据模型/管线 + swarmvault 晋升门槛 + nashsu 写入安全 + STORM 引用整合）
               ▲
        [联网采集层 P2] 开关受控的搜索/抓取/论文检索 → 调研任务（vane 三层开关 + httpx/trafilatura 栈）
               │
        [任务中枢 kb_job] 仿 ChatRun：job 表 + asyncio worker + 断点恢复
               │
        [MCP 工具面] kb.*/mem.*/collect.*/research.* —— 注册后 AI 聊天自动可调
               │
        [管理后台] 知识库/词条/任务/画像/设置 五页面（Vue3+EP，动态菜单零路由代码）
```

四层职责分离是本次调研最核心的结论：**记忆层（低权重、用户私有、易变）与 Wiki 层（高权重、可引用、可审计）必须分表分管；联网采集默认关；一切长任务进 job 表不阻塞聊天。**

## 三、数据模型（DDL 级设计）

> 全表带 `id/created_at/updated_at`（IDMixin+TimestampMixin），核心业务表加软删。SQLite + SQLAlchemy 2 async，插件隔离 MetaData。JSON 列统一 TEXT 存 JSON。

### 3.1 记忆层（P0）

```python
class KbEpisode:            # EverOS 式 episode 粗存：每会话一条摘要
    user_id: int            # 行级隔离
    session_id: str         # 关联 chat_session
    summary: Text           # 会话级摘要（1 次 LLM，便宜模型）
    status: str             # pending/analyzed

class KbMemoryItem:         # mem0 ADD-only 事实表 + graphiti 双时序
    user_id: int
    mem_type: str           # fact/preference/habit/event（habit 由频次聚合升级）
    content: Text           # 15-80 词自包含陈述（mem0 规格）
    confidence: float       # 0-1，来源次数加权
    source_count: int       # 证据次数（多来源提置信）
    access_count: int       # 召回计数（淘汰依据）
    valid_at / invalid_at / expired_at: datetime | None   # 事实轴/事务轴
    content_hash: str(32)   # MD5 去重（mem0 双重去重：库内+批内）
    session_id / message_id: str    # 溯源
    linked_ids: JSON        # 实体链接（mem0 linked_memory_ids 思路）

class KbProfile:            # EverOS 式 profile 单文件重写
    user_id: int  unique
    profile_md: Text        # 用户画像 Markdown（整体重写式，非追加）
    version: int
```

**记忆层管线**（worker 流程）：
1. 钩子事件入 `kb_job(type=memory_extract)` → 单次 ADD-only LLM 提取（`response_format=json_object`，json 解析双层降级：剥 code fence → 截首尾大括号 → 失败记 log 空过）
2. MD5 去重（库内 + 批内）→ 批量写 `KbMemoryItem`
3. 更新去重命中项的 `source_count/confidence`（去重即强化）
4. 每日（或每 N 次）画像任务：聚合 items → LLM 重写 `KbProfile.profile_md`（EverOS 离线引擎思想，成本后置）
5. 淘汰：`TTL 过期 + access_count 阈值` 标记 `expired_at`（自研，MindForge 无可抄）；`forget` API 显式遗忘（EverOS forget_session）

### 3.2 LLM Wiki 编译层（P1）

```python
class KbSpace:              # 知识库空间（聊天中可创建）
    user_id: int; name: str; description: Text
    status: str             # active/archived

class KbDocSource:          # 原始层（不可变，唯一真相源之一）
    space_id: int; title: str; url: str | None
    content_path: str       # 存储路径（raw/ 层，写后哈希校验）
    content_hash: str       # blake2b（增量失效判定，llmwiki-suite 三向比对：mtime+size+hash）
    source_type: str        # upload/chat/research/web/paper

class KbWikiPage:           # WeKnora wiki_page 模型直译
    space_id: int
    slug: str               # 空间内唯一（kebab-case）
    title: str; body_md: Text
    in_links / out_links: JSON          # 双向链接
    source_refs: JSON       # 来源 uuid|title 数组
    version: int            # 乐观锁，用户可见内容变更才 +1
    last_edit_source: str   # pipeline/agent/user/revert（四来源）
    status: str             # candidate/draft/live/archived（swarmvault 晋升 + PandaWiki 三态）
    confidence: float; source_count: int   # 晋升门槛数据

class KbWikiRevision:       # 两级保留（WeKnora：机器快照限 50/硬顶 200，保护人工编辑）
    page_id: int; version: int; body_md: Text
    edit_source: str; is_machine_snapshot: bool

class KbReviewQueue:        # 审批队列（内容寻址 id，nashsu 思路）
    space_id: int; page_id: int | None
    issue_type: str         # mixed_entities/contradictory_facts/out_of_date/broken_link/truncation
    detail: JSON; id_hash: str unique     # type+规范化标题哈希，重复问题不新建
    status: str             # open/resolved/dismissed
```

**编译管线**（`pipeline/compiler.py`，WeKnora Map/Reduce 裁剪版）：
1. 入队 `kb_job(type=wiki_ingest)` → debounce 聚批（默认 5 文档）
2. **dedup 预筛**：FTS5/trigram 相似召回 TopK=5（SQLite 替代 WeKnora pg_trgm）+ Jaccard 阈值 → **确定性拒绝规则先行，仅存疑项交 LLM 判合并**（省钱核心）
3. Map：候选 slug 提取 + entities/concepts 提取（1 次 LLM，json_object）
4. Reduce：per-slug 行级写锁（SQLite 单写者天然满足）合并已有页 → **page-merge 三层保护**（frontmatter 数组确定性 union / body LLM 合并 + **70% 缩水阈值拒绝疑似截断** / LOCKED 字段强制回写）
5. linkify：`[[wikilink]]` 双链回填，更新 in/out_links
6. lint：断链/orphan/矛盾三检（规则）+ 语义 lint（LLM）→ 入 `KbReviewQueue`
7. 新页落 `candidate` 状态，**晋升门槛**（swarmvault 六参数直译）：source_count≥3 且 confidence≥0.8 且 minAgeHours≥24 且 maxPerRun=25 → 用户一键批准转 `live`

**写入安全**（nashsu 红线机制的 MIT 等价实现）：
- LLM 输出按 `---FILE: wiki/<slug>.md---...---END FILE---` 协议解析；`is_safe_path()` 白名单校验（拒绝绝对路径/../ 逃逸）——防 prompt 注入写任意路径
- 乐观锁：写前比对 version，冲突返回 409 不静默覆盖（basic-memory 思路，独立实现）
- `last_edit_source` 服务端盖戳（云/MCP 写入强制 pipeline/agent，防伪造人工署名）

**引用整合**（`pipeline/citations.py`，STORM 纯 Python 移植）：正文 `[n]` 收集 → 超界删除 → URL 归并统一编号 → 按出现顺序重排 → References 节生成。**移植前先写回归测试**（调研遗留项）。

### 3.3 联网采集层（P2）

```python
class KbJob:                # 任务中枢（仿 ChatRun，含记忆层任务共用）
    user_id: int; space_id: int | None
    job_type: str           # memory_extract/profile_rewrite/wiki_ingest/wiki_lint/research/collect
    status: str             # pending/running/done/failed/cancelled
    payload: JSON; result: JSON; progress: int(0-100)
    step: str               # 当前步骤名（research 多阶段）
    token_usage: JSON       # in/out 计数（STORM LMConfigs.usage 思路）
    llm_calls: int          # 调用次数（成本护栏计数）
    error: Text | None

class KbCollectLog:         # 采集审计（联外行为全留痕）
    job_id: int; kind: str  # web/arxiv/openalex/semanticscholar
    url_or_query: Text; status_code: int; robot_respected: bool
```

**vane 三层开关**（全部落 `kb_settings`，前端 settings 页可视化）：
1. 用户级总开关 `web_enabled`（默认 **关**）
2. 聊天分类：skipSearch 结构化判断（规则：不确定=联网）→ 前端 composer 开关直传
3. **关闭时 MCP 工具不挂载/直接拒绝**（工具注册按开关条件化，LLM 看不见不可用，比 prompt 禁止可靠）
4. 护栏（对齐 Spring 版既有设计 + gpt-researcher 数值）：research 任务 LLM 调用 ≤30、单工具 ≤10、并发 Semaphore=5、单任务 token 预算上限、外发域名白名单 + robots 检查 + SSRF 校验（抄 `gpt-researcher/scraper/scraper.py:41-113` 防御集）

**采集栈**：
- 默认：`httpx`（显式代理配置 + `trust_env=False`）拉页 → `trafilatura.extract(html, output_format='markdown')` 纯函数 → 剥 YAML front matter → 入 `KbDocSource`
- 可选增强：crawl4ai（Apache-2.0 已验）作为 extras 依赖，JS 渲染需求时装 playwright 启用 `AsyncHTTPCrawlerStrategy` 或 vendor 其 markdown/chunking/filter 三模块
- 学术三源（`collector/academic.py`）：arxiv.py（**全局单例 Client**，3s 实例级限速）；pyalex（`config.email` 礼貌池 + `max_retries≥3` + 线程池包装）；semanticscholar（**外包共享限速器 ≥1s + retry≤3 + 连接复用**，三家最弱，最后接入）

**深度调研任务**（`pipeline/research.py`，STORM 骨架裁剪版）：
- 视角生成 1 次 → 大纲 2 次 → 分节成文每章 1 次（≈8-15 次 LLM，STORM 默认 45-50 次砍到 1/3）
- 每节采集结果经引用整合管线 → 产出草稿页（`status=draft`）→ **人工确认后才转 live**（危险操作确认原则）
- 断点续跑：do_research/do_outline/do_article 三段独立落盘（STORM engine 断点设计直译）

## 七、技术纪律（两轮调研的硬结论，开发全程遵守）

1. **依赖白名单**：核心仅 `httpx/trafilatura`（P2 起）；**禁入** langchain/langgraph/dspy/sentence-transformers/torch/everalgo；crawl4ai 仅 extras
2. **许可红线**：nashsu/llm_wiki(GPL)、BasicMemory/PandaWiki/SearXNG/MaxKB(AGPL/GPL) 五仓**只借鉴机制，零代码引用**；自研实现独立写
3. **LLM 成本纪律**：每任务调用数硬上限（json_object 输出、便宜过滤前置：hash/FTS 相似度/确定性规则先行，LLM 只兜存疑项）

## 十、公开知识库与晋升流（规划补充 · P1.5，约 3~4 天）

> **缺口确认**：原 P1 的 `kb_space` 只有 `user_id` 硬过滤 = 纯私库模型，
> 没有可见性维度、没有跨用户读取、没有「私库内容能否进入公共知识」的通道。
> 需求：①公开知识库（全员可读，AI 可召回）②AI 同时调用私库与公开库 ③私库内容可主动推送到公开库（需审核）。

### 10.1 借鉴的成熟模型（全部本地代码已取证）

| 借鉴点 | 来源 | 具体证据 |
|---|---|---|
| 可见性枚举（私/共享/公开） | MaxKB | `KnowledgeScope.SHARED / WORKSPACE`（knowledge.py:58-59） |
| 节点级三权限位（可问答/可访问/导航可见） | PandaWiki | `Answerable / Visitable / Visible`（node.go:85-87） |
| 发布三态 + 发布版本备份 | PandaWiki | 草稿/更新未发布/已发布 + NodeRelease（node.go:27-32,331） |
| 投稿 → 人工审核队列 | PandaWiki | contribution 审核队列（web/admin 投稿页） |
| 空间角色（owner/admin/contributor/viewer） | WeKnora | tenant_member.go:19-30 四角色枚举 |
| 资源×动作权限枚举 + 角色/直授权双通道 | MaxKB | permission_constants.py Group 枚举 + WorkspaceUserResourcePermission |
| 写保护：乐观锁 + 服务端署名盖戳 | Basic Memory（§AGPL 只读设计） | bm_write 独占创建 + expected_checksum；authored_by 服务端覆盖 |
| 晋升心智模型 | GitHub PR | 提交快照 → 审核 diff → 批准合并 → 来源溯源保留 |

> **晋升 = 知识库的 Pull Request**：私库词条提交的是「内容快照」而非引用，审核人看 diff 决定合入，
> 合入后在公开库生成独立副本并保留原作者署名与来源空间链接。这一心智模型贯穿表设计与 UI。

### 10.2 数据模型增量（P1 建表时一次到位，避免后续迁移）

```python
class KbSpace:                       # 改造现设计
    owner_user_id: int               # 原 user_id 语义化
    visibility: str                  # private（默认）/ shared（P3）/ public
    anon_qa_enabled: bool = False    # 是否允许匿名问答出口（P3，默认关）
    # public 空间：全员只读；写入仅经晋升流或空间维护者

class KbPromotion:                   # 晋升申请单（PR 模型）
    page_id: int                     # 私库源词条
    source_space_id / target_space_id: int
    status: str                      # draft / submitted / approved / rejected / withdrawn
    snapshot_md: str                 # 提交时内容快照（审核期间私库继续编辑不影响审核对象）
    snapshot_slug / snapshot_title: str
    submit_note: str                 # 提交说明
    submitted_by / reviewed_by: int
    review_comment: str
    published_page_id: int | None    # 批准后在公开库生成的页 ID
    id_hash: str                     # 内容寻址去重（同内容重复提交直接合并到已有申请）

class KbWikiPage:                    # 追加字段
    origin_space_id / origin_page_id: int | None   # 公开库副本 → 私库原页（溯源）
    origin_author_id: int | None                   # 原作者署名（晋升副本保留）
```

### 10.3 晋升流程（危险操作确认原则贯穿）

1. **提交**：私库词条页「推送至公开库」→ 选目标公开空间 → 写提交说明 → `kb_promotion(status=submitted)`，同时冻结快照
2. **审核**：有 `knowledge_base:promotion:review` 权限的维护者进入「待审」页，看到快照 vs 公开库现有同 slug 页的 diff（新增/修改/冲突三种情况）
3. **批准**：复制快照入公开库 → 生成 `kb_wiki_page(last_edit_source=user, origin_* 溯源字段)`，状态先落 `draft`（维护者一键发布为 live，参照 PandaWiki 三态）→ 回写 `published_page_id`
4. **拒绝/撤回**：留理由/可撤回，申请人收到结果
5. **约束**：公开库**只接受经晋升或维护者直接编辑的写入**（API 层硬校验）；私库原件不删除、不联动（双轨）

### 10.4 AI 召回双通道（kb_query 改造）

```
1. 私库检索：user_id == 当前用户（权重 1.0）
2. 公开库检索：visibility == 'public'（权重 0.9，SQL 硬过滤，绝无 private 泄漏路径）
3. 合并去重：同 origin_page_id 视为同源，保留私库版本；FTS5 + Jaccard 预筛
4. 结果标注：[私]空间名 / [公开]空间名，每条带 space + visibility 标签
返回结构：{"memories": [...], "public_pages": [{title, snippet, space}], "profile_excerpt": ...}
```

### 10.5 验收标准

- 私库词条推送 → 审核通过 → 公开库出现同内容页（带原作者署名 + 来源空间链接）
- 另一普通用户在聊天中让 AI 召回，能拿到公开库内容且标注来源；**召回不到任何 private 内容**
- 非维护者直接调用 API 写公开库 → 403
- 审核期间私库继续编辑 → 待审快照不变（snapshot 冻结验证）
- 公开库词条发布后，私库原页删除 → 公开库副本不受影响（独立副本验证）

| 期 | 公开库相关范围 |
